# Async handoff study

Source: Pulsar main87e75ec, production runtime scheduler3347942. The artifact is the same main-built artifact whose scheduler bytes were checked in the previous candidate study. Starlight comparator and environment are unchanged from that study. These are isolated single-location edit-latency fixtures, not a throughput ranking.

Conditions (all have the same new diagnostic Lightbench binary):

1. Legacy: unchanged scheduling, unload-budget await API followed by the existing global pending-work barrier.
2. Future: unchanged scheduling, repeatedly retrieve and await the existing private nearby-chunk future, then the same global barrier. No unload budget is consumed by this diagnostic wait.
3. Gated: exclude this world's workers before an edit, outside the timed interval; enqueue the entire edit; release the world inside the timed drain; await futures and the global barrier. This intentionally coalesces producer notifications before execution.
4. Caller: the same exclusion before the edit; enqueue the entire edit; use the same dispatcher claim, footprint reservation, paired-lane claim, engine pool and task execution method on the caller; check the same global pending-work barrier; release the exclusion after timing ends.
5. Gated polling: the same exclusion and release as gated; skip the unload await API and directly use the original global pending-work polling loop. This keeps the polling policy the same as legacy once its unload wait budget is exhausted.
6. Starlight: synchronous propagateChanges, unchanged reference classes.

Gated polling versus caller is the primary execution-placement comparison. Both have complete producer notifications available before execution. Gated versus gated polling controls the wait policy under the same held notification batch. These comparisons include the practical cost of releasing workers and waiting for completion, OS scheduling, and possible execution-thread locality/JIT effects. They are NOT an isolated cost per context switch, nor can the entire measured difference be labeled semaphore overhead. The gated release is inside its measured drain; caller exclusion cleanup is outside the measured interval, because it is not needed for that caller to observe completed light. Both pre-edit exclusion calls are outside timing. Their exclusion safety is tested independently, including progress of another world.

Future versus gated additionally changes batching/producer-consumer overlap. Legacy versus future isolates the completion-wait policy with normal production concurrency; the same scheduler diagnostic class is used in all five Pulsar conditions. It adds a synchronized owner check to claim and extracts the existing job body into execute; this study's legacy control is therefore a diagnostic build, not an untouched release artifact. No conclusions should be inferred by subtracting timings from earlier epochs. Six initial native runs and three pilots under the first harness prompted the addition of gated polling; they are retained separately under superseded and excluded. All final primary conditions use the same final harness binary.

The original main artifact and diagnostic artifact differ only in the scheduler and its Claim class. No production source is edited. For sampled follow-up runs, independent timing hooks from the prior warmed recorder are substituted in explicitly enumerated classes; the AxisDirection companion differs because its enclosing source's debug line numbers changed. The recorder is the existing shared schema3 deterministic phase/index sample (mask15), warmed and discarded before measuring. Sampled runs are separate from the uninstrumented primary latency comparison.

Sampled decomposition for each captured edit: submission; first task start minus submission (dispatch interval); sum of both lane task bodies; gaps between task bodies; native completion minus final task-body end (completion-observation tail). Gated/caller captures must have no overlapping tasks and first task start at or after submission. Exact native sample timing, positive exact warmup capture count, light verification, task/engine counts and queue-entry counters are validated. Queue-wait sums must not be treated as additive dispatch cost: a queued partner waits while the first lane executes.

Native summaries are medians of four fresh-JVM run means with run min/max. The last75% index sensitivity is retained as in earlier studies. Every edit has stored-light checks and every run has independent initial/final full-volume checks. A fixture does not establish correctness for arbitrary worlds/modpacks. The aggregate await counters include preparation, warmup and measurement; they do not by themselves locate every budget-exhaustion event in the measured region.

The `lightbench updates` command also records block-light phases with a different plan. Those extra phases remain in raw data and are validated, but are excluded from the primary block summaries and sampled work comparisons. Only the dedicated blockupdates family supplies block-placement/removal results; only the sky family supplies Sky-opening/closing results. These plans must not be pooled.

The follow-up list in the Pulsar repository defers propagation-loop, face-opacity and extra bookkeeping analysis. This study does not remove those features or attribute residual time to them.
